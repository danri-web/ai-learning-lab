## 1. 变更清单

| 原需求 | 变更为 | 为什么 | 影响 |
| --- | --- | --- | --- |
| SQLite + Drizzle ORM + SQL schema + migrations（ARCH-02 / DATA-03） | **不要求数据库**。`content/articles/*.md` 是笔记真相，`resources.json` / `tasks.json` 是资源与任务的真相；没有 DB、没有迁移、没有双写 | 单用户、单机、几百篇量级；文件可直接用任何编辑器读写，备份就是一个 zip；少一层“文件↔数据库同步”的故障面 | 删除数据库相关的“可重建缓存”承诺；D1 里“SQLite 只是缓存”降为**可选**，当前不实现 |
| SQLite FTS5 全文索引、增删改后索引同步、索引重建（S5-01 / S5-06 / S5-08） | **不建索引**。每次搜索直接扫 Markdown/JSON，子串匹配 + 摘要 + 高亮区间；增删改后下一次搜索立刻可见；“重新扫描”只是重跑查询 | 实测 2 篇笔记/2 条资源 **2.6–4.8 ms**；中文用子串比 FTS5 的 `unicode61`（中文 0 命中）和 `trigram`（2 字词差）更稳 | 不再声称有“索引更新/重建”；搜索耗时随文件数线性增长，超过 300 ms 再评估缓存（仍不改变真相来源） |
| 代码高亮用 **Shiki**（S3-08） | 用 `rehype-highlight`（highlight.js） | Shiki 在 Turbopack 下生成 `.next/<阶段>/node_modules/shiki-<hash>` 目录联接；第二次 dev/build 时 Windows `unlink` junction 必然 EPERM，只能手删 `.next` | 视觉上不是 VS Code 级 TextMate 语法，但同步、无 wasm、无 junction，构建稳定 |
| 文章 id 独立于标题与文件名，重命名不破坏身份（DATA-02） | **id = 文件名 stem**，创建后不再改名；改标题不改 id；重名自动 `-2` | 文件是唯一真相时，文件名本身就是最直接的身份；不需要“文件↔id”映射表，也不存在映射过期 | 外部重命名文件会让 frontmatter 的 id 失效（应用会明确报错，不静默接受）；要改名走“新建/删除”或手工同时改两处 |
| 业务 API 用 Next.js Route Handlers（ARCH-03） | 业务写入/搜索用 **Server Actions**；Route Handlers 只保留登录/登出与备份下载 | Server Actions 少一层手写 fetch/JSON，Next 自带 Origin 校验与渐进增强；认证/下载这类需要明确 HTTP 语义的仍用 Route Handler | API 形状与最初设想的 `/api/articles` 等不同；分层仍保持 action → service → storage |
| 页面不得直接读写数据库或文件（ARCH-04） | **写**必须经 `features/*/service.ts` → `lib/content/*`；**读**允许页面调用只读取数模块 | 页面是服务端组件，直接读只读模块少一层无意义的转发；写入仍只有一条路径，源码闸门守着 | 审计算“PARTIAL”的这一条按本变更视为已批准；写入分层不放宽 |

## 2. 没有变的安全要求（§8，逐条保留）

1. 默认只监听 `127.0.0.1`，不自动开放局域网或公网。
2. 局域网必须主动开启，并用生产构建与受保护的启动配置。
3. 受保护内容的读取与所有写入都要认证；删除、恢复还要授权检查。
4. 写操作有 CSRF / Origin 防护，请求体有上限（登录 8 KB；表单字段有长度上限）。
5. 外部输入校验（Zod；frontmatter 只允许 YAML/JSON，不执行代码）。
6. 禁止路径遍历、任意文件读写、危险 HTML 注入；frontmatter 也不得执行代码（D16）。
7. 外部链接只允许安全协议；收藏内容不执行。
8. 服务端不抓取用户提供的 URL（避免 SSRF）。
9. 密码、密钥、数据库、备份不进 `public/`、不提交 Git。
10. 备份覆盖 Markdown / JSON / `.trash` 留档；恢复要能验证（本变更只去掉“必须包含 SQLite”）。
11. 不直接暴露公网；不可信 Wi-Fi / 敏感数据要 HTTPS 或可信隧道。
12. 局域网 HTTP 不提供传输加密，文档与启动提示必须写明。

## 3. 没有变的功能验收（§13）

11 项不变：笔记 CRUD、Markdown/代码/公式/目录、资源收藏与筛选、标签/分类/搜索、任务与真实进度、
Dashboard 统计、Windows 稳定、Android 受保护局域网、未认证阻止、全量备份恢复、核心测试与可重装。
变的只是“用什么实现”，不是“能不能用”。

## 4. 验收口径

- 审计矩阵中 ARCH-02、DATA-03、S3-08、S5-01、S5-06、S5-08、ARCH-03、ARCH-04 等条目，
  按本变更视为**已批准的替代实现**，不再按原技术栈判 FAIL。
- 这不等于“审计作废”：SEC-01/02/03、QA-01/02/03 是真实缺陷，已修；DATA-01（恢复崩溃原子性）
  和独立运行时验收仍是待办。
- 不再对外声称本项目“使用 SQLite / Drizzle / FTS5 / Shiki”。README 与本变更保持一致。

## 5. 触发重新评估的信号

- 搜索单次 > 300 ms，或笔记/资源数量让扫盘明显变慢 → 评估 mtime+size 缓存，必要时再上 SQLite（仍只当可重建缓存）。
- 需要多用户、共享空间、跨设备同步 → 文件+JSON 的单用户模型不成立，重新设计。
- 需要稳定的“重命名不坏链接”身份 → 再引入独立 id 与映射表，而不是继续用文件名。
- Windows/Turbopack 对 Shiki 的 junction 问题被上游修复 → 可重新评估 Shiki，但要先跑第二次 build 回归。
