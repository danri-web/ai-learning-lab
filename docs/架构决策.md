## D1 · 文件是真相，SQLite 只是可重建的缓存

> **2026-10-30 变更**：SQLite 缓存从未实现；[`需求变更-2026-10-30.md`](需求变更-2026-10-30.md)
> 明确“不要求数据库”。D1 的“可重建缓存”降为**可选**（单次搜索 >300ms 时再评估），当前不实现。

**决定**：文章正文与元数据（标题/分类/标签）全部以 `content/articles/*.md` 的 frontmatter 为准。
数据库只存"能重建的东西"（搜索索引、将来的任务与收藏），任何一时刻删掉数据库，应用仍能工作。

**为什么**
- 数据所有权：用户能用任何编辑器改笔记、能用 git 管笔记，十年后仍读得出来
- 避免双写：两份真相必然产生**静默**不一致（改了文件、库里没变），而这种 bug 最难发现也最伤信任
- 库坏了不心疼：可以直接删掉重建

**后果**
- 列表读取 = 扫目录 + 解析 frontmatter（几百篇约几十毫秒，可接受）
- 写入 = 先写文件成功 → 再更新索引；**索引失败可容忍**，下次扫描自行修复
- 任何"以库为准"的便利功能（比如只改库不改文件）都不允许做

**回头改的信号**：目录扫描超过 300ms（大约 5000 篇以上），或用户开始抱怨列表慢。
那时加 mtime+size 的轻量缓存，**仍然不改真相来源**。

## D2 · 阶段 3 拆成 3a（只读）和 3b（写入）

**决定**：3a 只做"扫目录 + 解析 + 渲染 + 列表/详情"，不写任何文件；3b 才做编辑器、保存、删除。**（3a 已完成 2026-10-29）**

**为什么**
- 让"能看到真实内容"提前两三周出现，而不是对着一堆空状态想象
- 把最难返工的部分（Markdown 渲染、中文排版、代码高亮、TOC）前置 —— 这些改起来最贵
- 写入风险最高（动用户数据），放在最后，且闸门（`resolveArticleFile` / `writeFileAtomic`）已就位

**后果**
- 3a 完全不需要数据库（D1 的直接推论）
- 3a 结束时如果排版不满意，**不要进 3b** —— 否则写入做完还要回头改设计

**回头改的信号**：不存在（这是顺序，不是结构）。

## D3 · 文章 id = 由标题生成的 slug，创建时定下就不再改

**决定**：`id` 与文件名同一个东西（`transformer-basics.md`）。创建时由标题生成 slug，之后**标题怎么改都不重命名文件**；重名自动加 `-2`、`-3`。

**为什么**
- 人可读：在资源管理器里能认出是什么
- 稳定：id 不随标题变化 → 内部链接、收藏关联不会断
- 与 `lib/security/paths.ts` 的白名单 `[a-z0-9][a-z0-9-]{0,63}` 天然对齐

**后果**
- 需要处理重名
- ~~**未决问题（3b 前必须定）**：中文标题怎么生成 slug？~~ → **已由 D7 定案**（中文标题直接当文件名）
  - 拼音转写（要引入依赖，且多音字可能错）
  - 时间戳兜底（`note-20261029-ab12`，可读性差但零依赖）
  - 新建时让用户自己填（多一步操作，但最可控）

**回头改的信号**：如果开始频繁手动重命名文件来整理目录，说明"id 绑文件名"这个约束太紧。

## D4 · 写入入口：Server Action → service 层 → lib/content

**决定**
```
Server Action（app/(workspace)/**/actions.ts）
  └── features/<域>/service.ts      ← 业务规则，唯一决定"能不能写"的地方
        └── lib/content/*           ← 唯一碰文件系统的地方（走 resolveArticleFile + writeFileAtomic）
```
页面组件不得直接读写文件或数据库（需求书 §3 的要求，这里落成具体路径）。

**为什么**
- 少写一半代码：不用自己解析请求体、定错误格式
- Next 内建 Origin/Host 校验 → 阶段 7 的 CSRF 要求几乎白送
- 以后加 CLI 只是"另一个入口"，共用同一套校验和原子写入

**后果**
- 源码闸门已限制"只有 `lib/fs`、`lib/security/paths`、`lib/content` 能 import fs"；**3b 已落地第二条**：只有 `features/articles/service.ts` 能 import `lib/content/write` —— 页面想绕过 service 直接写文件，测试直接红
- 长任务（重建索引、备份）走 CLI 脚本，不走 HTTP

**回头改的信号**：需要外部脚本或手机快捷指令直接调 HTTP → 加一层 Route Handler 包同一个 service，不动下层。

## D5 · 笔记文件不进主仓库，放进独立的私有仓库

**决定**：`content/articles/` 被主仓库 gitignore；它本身是一个**独立私有 git 仓库**（和 `notes/`、`blog/` 同一模式：嵌套仓库 + 外层忽略）。

**为什么**
- 主仓库是**公开**的（GitHub `danri-web/ai-learning-lab`）：笔记一旦进主仓库就等于公开
- 独立私有仓库给到免费的版本历史 + 异地备份，同时不污染代码仓库

**后果**
- `clone` 主仓库后看不到任何笔记 —— 列表是空的（这是预期，不是 bug）
- 备份流程必须覆盖这个私有仓库（阶段 7）
- 想分享某篇笔记时，走"导出"，而不是"推仓库"

**回头改的信号**：如果开始想把笔记和代码一起版本化（比如想让别人看到示例笔记），
就加一个 `content/articles/_samples/`（单独例外放行），而不是把整个目录放回来。

## D6 · 中文搜索先用 LIKE，不急着上 FTS5

**决定**：阶段 5 先做 `LIKE` 全表过滤 + 前端排序；FTS5 作为"以后确实慢了再说"的备选。

**为什么**（都是实测，不是推测）
- FTS5 默认分词器 `unicode61` 对中文 **0 命中**（搜"注意力"找不到）
- 换 `trigram` 能用，但 **2 字词永远搜不到**（"模型""机制"全废），且中文 3-gram 索引体积膨胀明显
- 个人知识库规模（< 5000 篇）下，LIKE 的延迟完全可接受

**后果**
- 不需要维护索引一致性（正好符合 D1）
- 中文短词、子串匹配都天然支持

**回头改的信号**：搜一次超过 300ms，或用户开始要求"模糊/相关度排序"。
那时考虑 `Intl.Segmenter` 预分词（Node 内置，零依赖）+ unicode61，而不是直接上 trigram。

## D7 · 中文标题直接当文件名（取代 D3 的未决项）

**决定**：新建笔记时，`id` = 标题归一化后的结果：
1. NFKC 归一（全角 `ＡＩ` → `AI`）
2. 除了字母/数字/`-`/`_` 之外的一切连续字符折成一个 `-`（空格、冒号、括号、斜杠、emoji 都在内）
3. 去首尾 `-`、截到 64 位
4. 落在保留名上（`con`/`nul`/`com1`… 与路由保留字 `new`）就加 `note-` 前缀
5. 一个可用的字都没有 → 时间戳兜底 `note-20261030-ab12`

例：`Transformer 的注意力机制（上）` → `Transformer-的注意力机制-上.md`。
id 白名单从"纯 ASCII"放宽到 `[\p{L}\p{N}][\p{L}\p{N}\-_]{0,63}`。重名加 `-2`、`-3`。

**为什么**
- 可读性 > 自动化：这是用户每天在资源管理器里看的名字，`注意力机制.md` 比 `zhu-yi-li-ji-zhi.md` 和 `note-20261030-ab12.md` 有用得多
- 零依赖：拼音方案要引库，且多音字（银行/行走）会错，错在你天天看的文件名上
- 放宽的**只是字符集，不是结构**：点号、`/`、`\`、空格、控制字符、零宽字符仍然在白名单外 → `../` 这类路径穿越依旧进不来，`resolveArticleFile` 的物理校验也没动

**后果**
- 文件名、frontmatter 的 `id`、URL 里都会出现中文
- **实测坑（Next 16.4.3）**：动态段交给页面的 `params.id` 是**没解码的原始值**（`%E6%B3%A8...`），中文 id 会被路径闸门判成非法。所以页面入口统一走 `articleIdFromParam()`（含 `%` 才解码；id 字符集里没有 `%`，判据是安全的）。**升级 Next 必须重测这一条**
- 判重用"小写集合"：Windows 文件系统不分大小写，`Model.md` 与 `model.md` 是同一个文件，第二个自动变 `model-2`
- 标题里被折掉的字符不可逆（`注意力：机制` → `注意力-机制`），想保留原样只能改标题或手动改文件名
- 用户手写的额外 frontmatter 字段（比如 `reviewed: true`）在保存时**原样保留**，只覆盖 title/category/tags/updatedAt

**回头改的信号**：如果 URL 里的中文开始惹麻烦（分享链接被聊天软件截断、编码错乱），
就给"导出/分享"加一层 ASCII slug，而不是把文件名改回英文。

## D8 · 写入进程内串行 + 保存带版本校验（审计 v3 之后补的）

**决定**（两件，都是因为"写入会毁数据"）：
1. `lib/content/write.ts` 里所有会改磁盘的操作（新建/保存/删除）走**同一把进程内队列**（`serialize`）：
   分配 id 与落盘不能再被另一个请求插进来。
2. 编辑器打开时把**正文指纹**（sha256 前 32 位）放进隐藏字段 `base`；保存前比对磁盘上的当前指纹，
   不一致就拒绝（`reason: "stale"`），界面给出「仍然覆盖」按钮 —— 决定权在用户手里。
   不带指纹的调用（将来 CLI/脚本）不做检查，这是刻意的。

**为什么**
- 审计 v3 F1 实测：同一标题 8 路并发创建，**8 个请求都返回成功，磁盘上只剩 1 个 id**（7 份内容被静默覆盖）。
  原因不是原子写不够，而是"检查存在 → rename 顶替"是两步，中间能插进另一个请求。
- 审计 v3 F2 实测：两个编辑器先后保存，后保存的旧稿把新稿**静默**顶掉；外部编辑器改过、页面没刷新时同样如此。
  对"十年前写的笔记还要能打开"这个目标，静默丢失是最坏的一类。

**后果**
- 保存多读一次文件、算一次哈希（几十 KB，可以忽略）
- 外部程序的修改也会被算成"冲突"——这是对的：那确实是一次别人的写
- 没有版本历史可回退，所以「覆盖」必须由人显式点一次
- 跨**进程**的并发（两个 `next dev`、另跑 CLI）不共享这把队列，仍属残余 TOCTOU，已登记

**回头改的信号**：如果冲突提示频繁到让人烦（比如某个同步盘总在保存后重写文件），
再考虑"保存前自动重读+三方合并"——但那会引入真正的合并算法，代价远大于现在。

## D9 · 资源收藏：一个 `content/resources.json`，URL 只认 http/https

**决定**（阶段 4）：
1. 所有资源放**一个** `content/resources.json`（`{ version: 1, resources: [...] }`），和笔记一样
   **文件是真相**（D1）；这是个用户数据文件，主仓库 gitignore 掉，跟笔记一起备份。
2. URL **只接受 `http` / `https`**（`lib/security/resource-url.ts`）：`javascript:` / `data:` /
   `file:` / 相对路径 / 裸域名一律拒绝；**服务端永远不 fetch 用户给的地址**。
3. 写入复用笔记那套地基：进程内 `serialize`（D8）、`writeFileAtomic`、写前自检，
   外加单条资源的指纹（打开时记下，保存时比对，同 D8）。
4. 删除 = **先把整条记录追加到 `content/.trash/resources-deleted.jsonl`（带删除时间），再从数组移除**；
   活动 JSON 写失败时把刚追加的行撤回（审计 v4 F2：反过来会「记录没了、恢复副本也没写成」）。

**为什么**
- 几百条的规模下，一个 JSON 是**备份/回滚最便宜**的形态（拷一个文件就行），也能直接用任何编辑器修；
  没有"索引与文件不一致"的问题（D1 的红利），筛选/排序在内存里做，几百条是毫秒级
- 需求书 §8 要求避免 SSRF，而"只存链接、从不抓取"是最彻底的满足方式：没有请求，就没有 SSRF 面
- 拒绝 `file:` 是刻意的：浏览器对本地文件的策略各家不同，且以后加"打开链接"时要额外防

**后果**
- 改一条 = 重写整个文件（几百条约几十 KB；用原子写保证不会留半截）
- 文件坏了（非法 JSON / 结构不对）时应用**拒绝任何写入**，只在页面上报错 —— 不覆盖用户的坏文件
- 资源的 `id` 沿用笔记的规则（`lib/security/article-id.ts`），因为它是编辑页 URL 的一段
- 关联笔记是**逻辑关联**（存 `articleId`），不校验对方还在不在；断了就是列表上一条死链，不影响数据

**回头改的信号**：文件涨到 ~1MB、或保存一次超过 200ms、或开始需要"按标签统计/相关度"这类查询，
再按 D1 的原则加"可重建的索引缓存"（而不是换真相来源）；真到那一步再考虑 SQLite。

## D10 · 搜索不建索引：每次搜都扫盘，界面只拿摘要片段

**决定**（阶段 5，把 D6 落成具体形状）：
1. 搜索**没有索引**。每次搜索都扫一遍 `content/articles/*.md` + `content/resources.json`，
   归一成同一形状的文档后在内存里匹配。数据量大到确实慢时，只在这一层**下面**加
   mtime+size 缓存（可删可重建），上层一行都不改。
2. 匹配/摘要/高亮全在 `lib/search/query.ts` 这个**纯函数**里：输入文档、输出结果 + 区间。
   它不碰文件系统，所以能脱离磁盘测（中文 2 字词、大小写、代理对、区间合并都有断言）。
3. 客户端**只拿到摘要片段**（命中点前后 40/80 码元，且 ≤ 140 字符）与高亮区间 `{start,end}`，
   永远拿不到全文；高亮由前端切片 + `<mark>` 拼出来，不拼 HTML 字符串。
4. 需求书点名要的「索引重建」，在"没有索引"的前提下落成弹窗底部的 **「重新扫描」**
   —— 点一次重扫并刷新「已扫描 N 篇 / M 条资源 · X ms」。

**为什么**
- D1 的直接推论：文件是真相，就没有"索引与文件不一致"这一类**静默** bug。
  阶段 4 已经证明这类 bug 最贵（并发创建、过期保存都是它）。
- 中文短词只能靠子串匹配：FTS5 的 `unicode61` 实测 0 命中，`trigram` 搜不到「模型」这类 2 字词（D6）。
- 实测代价可以接受：2 篇笔记 + 1 条资源，端到端（扫盘 + 解析 + 匹配）6–16ms。
- 大小写不敏感用正则的 `i` 标志，**不**把两边 `toLowerCase()`：大小写折叠会改变字符串长度
  （`İ` → 两个码元），长度一变，高亮区间就整体错位。

**后果**
- 搜索的耗时随文件数线性增长，且每次都读全部正文（几百篇是几十毫秒级）
- 没有 TF-IDF / 相关度学习，只有"命中哪个字段"的固定权重（标题 1000 > 标签 300 > 分类 200 > 链接 100 > 正文 50）
- 结果上限 50 条，超出时界面明确写「只显示前 50 条」——不做分页，因为分页要有稳定的排序与总量
- 「索引重建」变成一个无意义的动作（所以叫「重新扫描」），这是**故意**的：需求书要的是"坏了能救"，而这里根本没有会坏的东西

**回头改的信号**：单次搜索 > 300ms（或者目录里上千篇），或开始要"相关度排序/模糊匹配"。
那时按 D1 加缓存（mtime+size）或 `Intl.Segmenter` 预分词，**仍然不改真相来源**。

**没有采纳的两条路（记下来免得下轮重议）**
- 不引 `cmdk`：它的筛选与排序假设了拉丁字母/空格分词，中文要绕过它反而更绕；
  键盘导航（↑↓ / Enter / Esc / IME 组字）本来就得自己控。
- 不加 `/api/search` 路由：与既有链路一致（D4 的入口规范）+ Next 内建 Origin/Host 校验顺手覆盖
  "别的网页偷偷打本地 3000 端口"这一类；只读，没有写面，等阶段 7 做认证时再统一收口。

## D11 · 学习任务：一个 `content/tasks.json`，三档状态，关联是可多选的逻辑关联

**决定**（阶段 6）：
1. 所有任务放**一个** `content/tasks.json`（`{ version: 1, tasks: [...] }`），形态与资源完全一致
   （D9 的地基）：文件是真相（D1），主仓库 gitignore，跟笔记一起进那个私有仓库。
2. 状态**只有三档**：`todo` / `doing` / `done`。需求书 §7 写明"不要做：甘特图、复杂项目管理、
   AI 排课、排行榜"，所以不加优先级、子任务、依赖关系这些一看就收不住的东西。
3. **截止日期可选**；逾期由 `dueInfo()` 现算，且**已完成的任务不喊逾期**。
   日期差用 UTC 算（夏令时不会把"差一天"算成"差 0.96 天"）。
4. **关联是多选数组**（`articleIds[]` / `resourceIds[]`），逻辑关联：只存 id，不校验对方还在不在；
   断链在界面上显示成「笔记已失效：xxx」，不崩页面、不自动删除。
5. 列表上改状态走**专门的** `updateTaskStatus`：只动 `status` 与 `updatedAt`，
   不重写表单里的其它字段 —— 否则在列表上点一下就把别处的草稿覆盖了。
6. 写入复用前三阶段的地基：进程内 `serialize`（D8）+ `writeFileAtomic` + 写前自检 + 单条指纹；
   删除 = **先**把整条记录追加到 `content/.trash/tasks-deleted.jsonl`，**再**从数组移除；
   活动 JSON 写失败时撤回追加行（同 D9 / 审计 v4 F2）。

**为什么**
- 与资源同一个形态 = 备份/回滚只要拷一个文件，也能用任何编辑器手改（本地优先的意义就在这）
- 三档状态是能"一眼看懂进度"的最少信息；多一档就要解释多一档（进行中 vs 阻塞 vs 待评审…）
- 关联用数组而不是单值：一个学习任务本来就对应"论文 + 教程 + 自己那篇笔记"这样一组材料
- 逾期只在**展示层**算，不落盘（不存 `overdue: true`）—— 存了就会和"今天"打架，第二天就变成谎言

**后果**
- 改一条 = 重写整个文件（几百条以内仍是毫秒级，与 D9 同一个理由）
- 没有"完成时间"字段：总览只统计"完成了几条"，不统计"本周完成几条"。
  真要周报再加 `completedAt`，那时它有明确的写入点（状态变成 done 的那一刻）
- 任务**不进** `Ctrl+K` 搜索：阶段 5 的范围是"文章与资源"（需求书 §7）；扩源要改 `lib/search/sources.ts`
- 没有提醒/通知：逾期只在页面上标红，不会弹窗、不会发邮件

**回头改的信号**：任务数破千，或开始需要"按项目分组 / 依赖 / 重复任务"，
那时应该先加一个项目维度，而不是把这张表改造成项目管理工具。

## D12 · 局域网认证 + 备份/恢复事务（阶段 7）

**决定**（这是一组绑在一起的决定，因为它们共同定义"数据与访问的边界"）：

1. **默认仍然只听 `127.0.0.1`**。局域网是显式动作：`npm run start:lan`，用**生产构建**，
   自己把 `ALLOW_LAN=1` 与绑定 `0.0.0.0` 一起打开；启动前检查 `LAB_PASSWORD_HASH` 与
   `SESSION_SECRET`，缺一个就退出。**配置不齐时 fail closed**，绝不退回「不登录也能看」。
2. **单用户口令 + 无服务端会话表**。口令只存 scrypt 哈希在 `.env.local`，格式
   `scrypt:N:r:p:<salt>:<hash>`（**用冒号，不用 `$`**：Next 会展开 `.env` 里的 `$VAR`，
   `$32768` 会被吃掉）。会话 cookie 是 HMAC-SHA256 签名的 `{v,sub,iat,exp}`，12 小时，
   HttpOnly + SameSite=Lax；换 `SESSION_SECRET` = 全端退出。登录失败 5 次锁 5 分钟（进程内全局桶，见 D13）。
3. **三道门**：`proxy.ts`（Next 16 的 Proxy，默认 Node 运行时，能读运行时 env）→
   工作区布局的 `requirePageAuth()` → 每个 Server Action / 受保护 Route Handler 里的
   `requireAuth()`。只读的 `searchAction` 也算受保护内容，一样要门。
   `/login`、`/api/auth/login`、`/api/auth/logout` 公开；其余全部要会话。
4. **备份 = zip + manifest**。`content/` 下白名单文件（Markdown 含 `_` 草稿、
   `resources.json`、`tasks.json`、`.trash/` 留档）打进 `backups/ai-lab-<时间戳>.zip`，
   根目录 `manifest.json` 记录版本、时间、每个文件的 sha256。**不含 `.env.local`**；
   `content/.trash/restore-*` 是恢复时的二级副本，不纳入后续备份。建完立刻重读并逐文件校验，
   失败就删掉这份新备份。
5. **恢复是一笔事务**：只从 `backups/` 列表选（不接受上传）→ 预览 diff（新增/覆盖/相同/删除）
   → 用户确认时带 `planHash` → 重算 diff 比对 → **先建 `pre-restore-*.zip` 快照并回读校验**
   → 预检所有目标（父目录不能是 junction/symlink、目标不能是链接/目录；**删除目的地也必须在写第一个字节前检查**，见 D13）→ 原子写入 →
   重扫比对 sha256 → 任一步失败用快照回滚。**删除默认不勾选**；勾选后移进
   `content/.trash/restore-<时间>/`，不是真删。整个过程走 `serialize`（D8 同一把锁）。
6. **安全响应头**：X-Frame-Options DENY、X-Content-Type-Options nosniff、Referrer-Policy
   no-referrer、Permissions-Policy、COOP/CORP、关掉 `X-Powered-By`。**CSP 暂不做**：Next 的
   启动脚本是内联的，严格 CSP 要 nonce 并卷进 proxy 与所有页面；而本项目不渲染用户 HTML
   （源码闸门禁 `dangerouslySetInnerHTML`），局域网也不对公网。
7. **不做可视化回收站**。需求书 §7 没有这项，做它要新开三条写路径（笔记/资源/任务各自回填），
   风险大于收益。整库快照 + 回滚已经覆盖"误删能回去"；单条 `.trash` 的恢复仍按原约定手动拖回。

**为什么**

- 需求书 §8 要"默认仅本机、局域网须主动开启并保护、读取与写入都要认证"；把"打开"收敛到
  一个脚本里，才能保证 0.0.0.0 永远不会被顺手打开。
- 备份/恢复是本项目第一次**成规模地覆盖 `content/`**。如果恢复不是事务，一次坏 zip 就能把
  用户积累的笔记冲掉；所以校验、快照、预览、回滚必须都在写第一个字节之前/之后有明确位置。
- 口令与会话都自己实现（scrypt + Web Crypto HMAC），不引 `jose`/`bcrypt`，是为了 Windows
  本地环境零原生依赖；代价是只支持单用户、没有角色/多设备管理，这是 MVP 的边界。
- 备份放 `backups/`、不传任何地方，符合 local-first；明文是刻意的（用户要能用任何解压工具打开），
  所以文档反复说"别放公开同步盘"。

**后果**

- 局域网模式与 dev 是两条路：`npm run dev` 永远不会开 0.0.0.0；`start:lan` 必须先 `build`。
- `.env.local` 不进 Git、也不进备份；换机/重装后要重新跑 `npm run auth:set-password`。
- 恢复只能从 `backups/` 里选：从 U 盘恢复要先手动把 zip 放进去（这是攻击面最小的做法）。
- 备份不自动清理；`backups/` 会一直长。数据小，先手动删。
- 恢复期间不要用另一个进程/另一台设备写同一个 `content/`：跨进程仍不共享 `serialize`。
- CSP、HTTPS、多用户、审计日志都不在阶段 7；局域网 HTTP 只适合可信 Wi-Fi。

**回头改的信号**

- 开始想在公网/不可信网络访问 → 必须上 HTTPS（反向代理或隧道）+ CSP nonce，不能只靠口令。
- 备份目录超过几百 MB，或开始需要"保留最近 N 份" → 加保留策略（而不是删快照）。
- 出现第二个用户/共享空间 → 现在的单口令模型不成立，得上账号与授权（P4）。
- 恢复开始被频繁使用（比如每周回滚）→ 说明平时写入流程有问题，先查根因，别把恢复当备份用。

## D13 · 审计 v4 后的三条修正（2026-10-30）

**决定**（三条都先写了复现，看着它失败，再改）：

1. **恢复：删除目的地也在写第一个字节前预检**。`content/.trash/restore-<时间>` 如果是普通文件/链接，
   必须在任何文章写入之前就报错；`PreflightError` 只允许发生在「一个文件都没写」的阶段，
   这样外层「content/ 没有改动」的话术才成立。
2. **资源/任务删除：先写恢复副本，再写活动 JSON**。顺序是「整条记录追加到 `.trash/*-deleted.jsonl`
   → 从 `resources.json` / `tasks.json` 移除」；活动 JSON 写失败时把刚追加的行撤回。
   任何失败之后，记录至少在活动数据或 `.trash` 中的一处。
3. **登录限速：全局桶，不读客户端转发头**。直接暴露的 `next start` 前面没有可信反向代理，
   `X-Forwarded-For` / `X-Real-IP` 都可以被客户端改；按它们分桶等于让攻击者换头绕过 5 次锁。
   单用户应用用固定 key `owner`，所有尝试共用 5 次 / 5 分钟。

**为什么**

- 审计 v4 F1 复现：固定时间戳 + 在 `content/.trash/restore-<stamp>` 放普通文件 → 文章已经写入，
  外层却报「没有改动」并跳过回滚。根因是「写入」在「删除目的地检查」之前。
- F2 复现：把 `.trash` 做成普通文件 → 删除返回失败，但 `resources.json` / `tasks.json` 已经空了。
  根因是「先删主数据、后写恢复副本」。
- F3 是源码层：`clientKey` 先读 `x-forwarded-for`，换一个值就是新桶。

**后果**

- 恢复失败时可能留下空的 `content/.trash/restore-*` 目录（没有文件），但不会再有「写完才报没改动」。
- 删除多一次 `.trash` 写入；撤回也失败时恢复行仍保留（宁可重复，不可丢）。
- 全局桶的代价：攻击者可以故意失败 5 次把房主锁 5 分钟（可用性 DoS）。
  换来的是「换头不能绕过穷举」。如果将来真的放到可信反向代理后面，再加显式 `TRUST_PROXY` 分支，
  而不是现在猜。

**回头改的信号**

- 出现第二个用户/多实例 → 全局桶和进程内 Map 都不成立，得上共享存储/账号维度。
- 恢复失败后仍看到「部分文章已写、错误却说没改动」→ 先查是不是又有 `PreflightError` 在写之后抛出。
- 登录锁频繁误伤房主（而不是攻击者）→ 说明该加「可信代理 + 账号维度」而不是继续放宽。

## D14 · 阶段 8：E2E 隔离、系统 Chrome、可访问性门槛与错误边界（2026-10-30）

**决定**（四件，共同定义"测试怎么跑、什么算通过"）：

1. **E2E 永远不在真实项目目录里跑**。`scripts/e2e-server.mjs` 把当前工作树复制到仓库外的一次性副本
   （默认系统临时目录，`E2E_SCRATCH` 可指定），用 `e2e/fixtures/content/` 覆盖副本的 `content/`，
   再复制 `node_modules`（Windows 用 `robocopy /MT`）。脚本先撞**安全闸门**：副本路径落在仓库里
   就直接退出；`app/` 已存在但没有所有权标记 `.ai-learning-lab-e2e` 时也拒绝删除
   （防止 `E2E_SCRATCH` 误配到另一个恰好有 `app/` 的项目根）。两条闸门都由
   `tests/e2e-safety.test.ts` 用真进程撞过；真实 `content/` 在整套 E2E 里是只读的。
2. **浏览器用系统 Chrome（`channel: "chrome"`），不下载 Playwright 自带的 Chromium**。
   两个 project：Windows 桌面 1440×900、Pixel 7（412×915，触摸）。写入/认证/a11y/性能只在桌面跑；
   Pixel 7 只做冒烟（五页导航、控制台错误、横向溢出）。Android 真机已在 2026-10-30 完整验过，
   E2E 不假装覆盖真机。
3. **可访问性用 axe 扫 WCAG 2 A/AA，只把 critical / serious 当失败**。扫描范围：七个页面 +
   搜索弹窗 + 局域网登录页；moderate / minor 打印但不拦（本地单用户应用里有一批评分标准没有决策价值）。
   自动扫描**不替代**读屏与真实键盘流程，这一点写进 README「已知问题」。
4. **错误边界 `app/error.tsx`**：client 组件，显示"数据没被改"、`digest`、重试与回总览两个出口；
   **不 import AppShell**（服务端组件，client 边界里 import 会构建失败）。证明方式是在 `_scratch`
   副本里故意 `throw` 后重新构建截图，真实仓库不插桩。

**为什么**

- E2E 的写入、删除、恢复都是真的。只要有一次跑在真实 `content/` 上，就可能把用户笔记覆盖掉 ——
  这是本项目最贵的事故类型，所以隔离要做成"跑错地方直接拒绝"，而不是"记得别跑错"。
- 目录联接在 Turbopack 下行不通（实测：`Could not find the Next.js package`），所以 node_modules
  必须真实复制；robocopy 多线程把 36k 文件的复制从 ~45 秒压到 ~6 秒，E2E 才敢每次跑。
- 系统 Chrome 少一份 150MB 的二进制、少一条"浏览器版本漂移"的维护线；Windows 上 Chrome 本来就在。
- 可访问性若把 moderate/minor 也算失败，第一次扫就会红一片"区域没有 landmark"这类建议，
  闸门很快会被无视；只拦 critical/serious 才能长期跑下去。
- React 19 的 form reset 是阶段 8 抓到的真 bug：text input 会被 React 写回，但 `<select>` / radio
  的 value 没变时不会重写 DOM —— 校验失败后控件看起来被清空（state 其实还在）。修法是失败后把
  DOM 同步回组件 state（只操作 DOM，不 setState），并由 E2E 钉住。

**后果**

- `npm run test:e2e` 单轮约 2.5 分钟（构建 66–71 秒是主要成本）；改测试时用 `E2E_REUSE=1` 复用构建。
- E2E 不进 `verify`：会起服务、会改测试数据，塞进每次提交会让人开始跳过闸门。
- 端口固定 3210 / 3211，不碰真实 dev 的 3000；两个实例都用生产构建，3211 的 `ALLOW_LAN=1` 让认证
  跑在真实 proxy 上（不是 mock）。
- 副本不清理（留在临时目录），下次运行会先删再建；`_scratch/ai-lab-e2e` 可以整个删掉。
- 错误边界只覆盖根布局以下；根布局自己抛错仍需 `global-error.tsx`，这一条留在不做的清单里。
- a11y 只有自动扫描；读屏、键盘全流程、中文输入法组字仍是人工项。

**回头改的信号**

- 界面稳定到"改样式基本不预期变化" → 再加视觉回归（截图对比），否则现在的红只会是噪音。
- 出现 CI（或第二台机器要复现）→ 把 `verify` + `test:e2e` 接进去，并给 E2E 缓存 node_modules。
- 开始支持 Firefox / Safari / 第二个用户 → 浏览器矩阵与认证模型都要重新评估，不是加个 project 的事。
- axe 的 moderate 里出现真实影响（比如新增表单没有 label）→ 把该规则单独提升为失败，而不是整体收紧。
- 根布局出现真实错误（字体、metadata、全局 provider）→ 补 `app/global-error.tsx`，别指望 `app/error.tsx`。

## D15 · 审计 v5 后的 E2E 隔离修正（2026-10-30）

**决定**（三条都先写复现/变异，看着测试变红，再改）：

1. **所有权与物理路径校验必须在复用分支之前**。`E2E_REUSE=1` 过去直接跳过 `prepare()`，
   也就跳过了所有权检查：只要目标目录里有 `.next/BUILD_ID`，就会拿一个未标记的 `app/`
   （可能装着真实笔记）起服务并写入（审计 v5 F1）。现在 `main()` 的顺序是：
   词法检查 → 创建 scratch → **`realpath` 物理检查** → **独占锁** → 所有权检查 → 端口检查 →
   （复用或复制/构建）。复用只复用**构建**，并强制重置 `content/` 与 `backups/`；
   复用结果只用于调试，不作为验收依据。
2. **路径检查分两层：词法 + 物理**。词法检查（`path.resolve`/`relative`）只看字符串，
   一个指向仓库的目录联接（junction）就能让 `E2E_SCRATCH` 在字符串上位于仓库外、实际落在仓库里，
   随后 `removeApp()` 会删掉真实 `app/` 源码（F2）。现在删除前把 SCRATCH 与 APP 都
   `realpath` 成真实路径，和仓库真实路径做**双向**包含判断；`app/` 必须是普通目录、
   标记必须是普通文件（链接/目录不算），词法检查保留为第一道。
   另外：Windows junction 在 `lstat` 里可能显示为普通目录（本机实测 `isSymbolicLink=false`），
   所以用 `realpath(APP) !== APP` 判链接，不能只信 `lstat`。
3. **同一份 scratch 同时只允许一个 E2E 进程**。两个 Playwright 共用默认副本时会互相删文件/构建
   （F3）。主锁用 `wx` 原子创建并写 PID：活 PID 直接拒绝，空锁 fail closed，死 PID 自动回收；
   但回收必须持有 `wx` 创建的**回收守卫**，同一时刻只有一个回收者，回收前重读并再判活，
   防止删掉刚被替换的活锁（审计 v6 P2）。子进程意外退出会让 supervisor 一起失败；
   端口检查挪到删除/复制之前，端口被占时不会白删一份副本。
   锁协议抽在 `scripts/e2e-lock.mjs`；两个回收者的交错由 `tests/e2e-lock.test.ts`
   通过阶段钩子（afterRead / afterReclaim / beforeCreate）做确定性覆盖。

**为什么**

- 这三条的共同点是"测试基础设施自己成了数据风险"。E2E 是唯一会真的执行恢复、删除的自动化，
  它的隔离如果只靠"记得别跑错"，一次误配就能毁掉真实笔记或别人的项目。
- 所有权标记只能防"手滑指错目录"，不能证明物理身份；所以物理路径和标记要一起用，
  而且要把标记当**护栏**而不是安全凭据（审计 v5 的原话）。
- 复用构建是为了改测试时省 70 秒，但"复用"不该等于"继承上一轮的脏数据"；
  重置夹具后，复用至少不会让测试结果依赖上一轮。

**后果**

- 默认副本固定在系统临时目录；两个 E2E 同时跑会直接报"另一个 E2E 正在使用同一份副本"，
  要并行就各自给 `E2E_SCRATCH`（目前没有分片需求）。
- `E2E_REUSE=1` 不重建，源码改动后必须去掉它再跑；文档已写明"只用于调试"。
- 物理检查与 `removeApp()` 之间仍有 TOCTOU 窗口（另一个进程在这两步之间替换目录），
  本地单用户测试接受这个窗口；真要多用户/并行再上文件锁或一次性容器。
- Playwright 在 Windows 上会强杀 webServer（收不到 SIGTERM），每轮结束通常会留下锁；
  下一次启动会自动回收（回收守卫串行）。**空锁 fail closed**；**回收守卫残留只会挡住「旧锁回收」
  这条路径**（主锁不存在时正常启动仍能拿锁），但下一次遇到死主锁就需要人工删守卫。
  PID 被系统复用时仍可能误判"仍在运行"，这是"宁可不跑，也不误删"的取舍。
- 复制过滤仍是"排除名单"（`.env*`/重目录/`*.tsbuildinfo`），
  `*.pem`、`.npmrc` 等未跟踪文件仍可能进临时副本；本机临时目录、不上传，属已知残余。

**回头改的信号**

- 需要并行跑多个 E2E 分片 → 每个分片独立 scratch + 独立端口，而不是放宽锁。
- E2E 要跑在 CI/容器里 → 物理路径与锁的假设要重新验（Linux symlink、只读文件系统）。
- 有人把 `E2E_REUSE=1` 当成验收结果 → 在输出里加显式"调试模式，不代表当前源码"提示，
  或直接移除复用。

## D16 · 外部验收审计（2026-10-30）：frontmatter 执行、登录入口与三个 UX 缺口

**决定**（每条都先按审计给的样本复现，再修；回归测试先看着红）：

1. **frontmatter 只解析数据，不执行代码**。`gray-matter` 4.0.3 对 `---javascript` / `---js`
   会走 JavaScript 引擎并动态执行；`matter.stringify(body, data)` 传字符串时还会先解析正文。
   现在 `lib/content/frontmatter.ts` 只允许 YAML/JSON，其它语言在进入解析器前拒绝；
   写路径改成 `matter.stringify({ content }, data)`，不再解析正文。覆盖读、搜索、
   保存、恢复预览、备份校验。回归：`tests/frontmatter-security.test.ts`（断言执行标记保持 0，
   而不是只断言“被拒绝”）。
2. **登录入口：先限字节，再占坑**。`request.formData()` 前加 8 KB 流式上限（Content-Length
   可撒谎、chunked 也要算）；限速改成 `check`（只读预检）→ 读体 → `beginAttempt`（pending 占坑）
   → 密码校验 → 结算。并发请求最多 `maxAttempts` 个进入验证，避免 100 个请求一起跑哈希。
   回归：`tests/request-body.test.ts`、`tests/auth-rate-limit.test.ts`、`tests/auth-login-route.test.ts`。
3. **三个 UX 缺口**：TOC 的围栏改成“字符 + 长度”状态机（支持 `~~~` 与 4 个以上反引号）；
   笔记详情在窄屏加可折叠目录；三个表单抽出 `useUnsavedGuard`，站内 `<Link>` 跳转也会提醒，
   不只依赖 `beforeunload`。回归：`tests/toc.test.ts` + E2E。

**为什么**

- 审计的 SEC-01 不是理论风险：同一段 Markdown 用项目锁定的依赖跑，执行标记确实被置 1；
  拒绝、Zod、前端转义都发生在执行之后，救不了。
- SEC-02/03 是公开登录路由的可用性边界：不做字节上限，局域网可以拿超大表单打内存；
  不在异步哈希前占坑，5 次限制在并发下形同虚设。
- TOC 的 `~~~` 会把代码块里的假标题带进目录，真实标题的锚点被挤成 `-1`；移动端目录
  是需求书 §6 明写的；站内跳转丢草稿是用户实际会遇到的。

**后果 / 未修（不要假装都修了）**

- 恢复仍**不是崩溃原子**：进程/系统在两次 rename 之间被杀，可能留下混合数据；
  `pre-restore` 快照能手动回滚，但没有 durable journal + 启动自动恢复（DATA-01，待定）。
- 跨进程写 JSON 仍不互斥（DATA-02，ADR 残余风险，已有记录）。
- SQLite / Drizzle / migrations / FTS5 / Shiki 仍是相对**最初需求书**的偏离（REQ-01）。
  **2026-10-30 已按 A 正式变更**，见 [`需求变更-2026-10-30.md`](需求变更-2026-10-30.md)；
  安全要求与 §13 验收清单不放宽。

## 偏离需求书的记录（有意为之，不是遗漏）

| 需求书写的 | 实际用的 | 为什么 |
| --- | --- | --- |
| 代码高亮 **Shiki** | `rehype-highlight`（highlight.js） | Shiki 在 Turbopack 下被当成外部包，生成 `.next/<阶段>/node_modules/shiki-<hash>` 目录联接；Turbopack 下次启动会对它 `unlink`，而 Windows 对 junction 调 unlink 必然 EPERM —— **第二次 dev / 第二次 build 都起不来**（只能每次手动删 `.next`）。highlight.js 同步、无 wasm、无 junction；配色在 `app/globals.css` 里映射到设计令牌 |
| （未规定）Cache Components | `cacheComponents: false` | shadcn init 默认打开。开启后动态页必须写成 `<Suspense>` + `connection()`，与"整页 force-dynamic"互斥（构建直接报 `connection() accessed outside of <Suspense>`）。本地数据应用要的是"每次请求都读盘"，不是流式壳 |

**两处实现约束（不算偏离，但要知道）**：

- `lib/content/articles.ts` 里的 `articlesRoot()` 把 `content/articles` 写成**字面量**：Turbopack 静态分析不接受"用变量拼路径"，否则构建警告"会追踪整个项目"（实测会让 build 失败）。
- 读目录 / 读文件带 `/*turbopackIgnore*/`：正文是运行时读的用户数据，不该被打进产物。

## 残余风险登记（明知未解决，别再假装）

| 风险 | 现状 | 什么时候处理 |
| --- | --- | --- |
| **恢复不是崩溃原子** | 逐文件 rename；失败走 catch 回滚，但进程/系统在两次 rename 之间被杀会留下混合数据；`pre-restore` 快照可手动回滚，没有 durable journal / 启动自动恢复（审计 DATA-01） | 需要"强杀也能自动恢复"时再加 journal + 启动恢复；先只承诺"普通失败自动回滚" |
| **TOCTOU：路径校验与真正读写之间有窗口** | 接受（本地单用户） | 如果将来多用户/多进程写同一目录 |
| **跨进程并发写**（两个 `next dev` / 另跑 CLI 写同一目录） | 进程内已串行（D8），跨进程仍是同一个窗口；局域网模式只跑一个 `next start`，恢复也拿同一把锁 | 真要支持时上文件锁（`proper-lockfile` 之类），而不是自己造 |
| 硬链接无法用 realpath 区分 | 不在防线内（它不能把写入搬出目录） | 不需要 |
| 目录没有 fsync | 未做（Windows 上收益接近零） | 如果将来要跑 Linux 服务器 |
| 无 CSP / 基础安全头 | 基础头已加（XFO/nosniff/Referrer/Permissions/COOP/CORP，D12）；**CSP 未做**（Next 内联启动脚本要 nonce，会卷进 proxy 与所有页面） | 真要上 HTTPS/不可信网络时一起做 CSP nonce |
| **错误边界只覆盖根布局以下** | 已加 `app/error.tsx`（D14）；根布局自己抛错仍会走 Next 默认页，需要 `global-error.tsx` | 根布局出现真实错误时再补 |
| 源码闸门是正则，不是沙箱 | 已知能绕过的形态已记录在测试里；阶段 8 用真实生产构建的 E2E 补了"端到端行为"这一层，但仍不是沙箱 | 不计划改成沙箱；真要做就在构建期加第二道检查 |
| **文件级符号链接的写入防护未经本机实测** | 本机建不出文件级 symlink（需管理员/开发者模式），对应断言显示 **skipped**（不是通过） | 任何能建的机器上会自动执行；在受限环境里必须看跳过的数量，不能只看绿色 |
| **未保存提醒的边界** | `beforeunload` + 站内 `<a>` 点击拦截（D16）；浏览器后退/前进、外链、新标签页不拦；保存本身仍有 D8 的版本校验兜底 | 如果真丢过一次内容，再上路由级拦截 |
| **删除的可恢复性只靠目录约定** | 单条文件仍进 `content/articles/.trash/`；**整库**可用 `pre-restore-*.zip` 回滚（D12） | D12 定案：不做可视化回收站（需求书没有，且要多开三条写路径） |
| **`.trash/` 会进那个私有 git 仓库** | 删除 = 多一个被跟踪文件，历史只增不减；"恢复"与 git 历史两套语义并存 | D12 定案：保持跟踪；备份包含 `.trash/`，恢复时挪出的 `restore-*` 不纳入后续备份 |
| **资源删除的恢复只能手工** | 记录在 `content/.trash/resources-deleted.jsonl`，界面没有"回收站"；整库快照可回滚，单条仍要自己贴回 JSON | D12 定案：阶段 7 不做单条回收站；需要时进 P1 |
| **资源的关联笔记可能是死链** | `articleId` 只校验格式，不校验存在；笔记被删/改名后列表上会有一条点不开的链接 | 阶段 6 做任务关联时一起解决（或加"悬空引用"提示） |
| **Server Action 的 CSRF** | 阶段 7 用 `proxy.ts` + Server Action 内建 Origin/Host 校验 + 登录/登出显式 Origin 检查；用跨站 curl 与浏览器实测过。`Origin: null`（沙箱/代理）按缺失处理，登录仍需口令 | 若将来支持多用户，收紧 Origin 策略并加 CSRF token |
| **登录失败限速是进程内全局桶** | 连续 5 次锁 5 分钟，所有来源共用一个桶（D13）；不读 `X-Forwarded-For` / `X-Real-IP`；重启清空，多进程不共享；攻击者可故意失败锁住房主 5 分钟（DoS） | 单用户单进程够了；真放到可信代理后 + 多实例时再换共享存储 |
| **`Origin: null` 被当作缺失** | 沙箱 iframe/某些代理会发 `Origin: null`；登录仍需正确口令，风险限于"登录 CSRF"（单账号无意义） | 多用户后改为拒绝 `null` 或校验 `Sec-Fetch-Site` |
| **备份是明文 zip、不自动清理** | `backups/` 已 gitignore；内含全部笔记，别放公开同步盘；没有保留策略，会一直长 | 数据量变大时加"保留最近 N 份"（先文档化再实现） |

| **Proxy 依赖 Next 16 的 Node 运行时** | 阶段 7 用 `proxy.ts`（Next 16 把 middleware 改名 Proxy，默认 Node）；运行时 `process.env` 可读 | 升级 Next 必须重测 proxy 的 runtime 与 matcher |
| **搜索每次都读全部正文** | 无索引（D10），耗时随文件数线性增长；几百篇是几十毫秒 | 单次 >300ms 时按 D1 加 mtime+size 缓存 |
