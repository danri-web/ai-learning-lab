> 加新决策时往下追加，不要改写已生效的条目（要改就在下面加一条"取代 D3"）。
> 最后更新：2026-10-30（阶段 3b 完成）

## D1 · 文件是真相，SQLite 只是可重建的缓存

**决定**：文章正文与元数据（标题/分类/标签）全部以 `content/articles/*.md` 的 frontmatter 为准。
数据库只存"能重建的东西"（搜索索引、将来的任务与收藏），任何一时刻删掉数据库，应用仍能工作。

**为什么**
- 数据所有权：用户能用任何编辑器改笔记、能用 git 管笔记，十年后仍读得出来
- 避免双写：两份真相必然产生**静默**不一致（改了文件、库里没变），而这种 bug 最难发现也最伤信任
- 库坏了不心疼：可以直接删掉重建

**后果**
- 列表读取 = 扫目录 + 解析 frontmatter（几百篇约几十毫秒，可接受）
- 写入 = 先写文件成功 → 再更新索引；**索引失败可容忍**，下次扫描自行修复
- 任何"以库为准"的便利功能（比如只改库不改文件）都不允许做

**回头改的信号**：目录扫描超过 300ms（大约 5000 篇以上），或用户开始抱怨列表慢。
那时加 mtime+size 的轻量缓存，**仍然不改真相来源**。

## D2 · 阶段 3 拆成 3a（只读）和 3b（写入）

**决定**：3a 只做"扫目录 + 解析 + 渲染 + 列表/详情"，不写任何文件；3b 才做编辑器、保存、删除。**（3a 已完成 2026-10-29）**

**为什么**
- 让"能看到真实内容"提前两三周出现，而不是对着一堆空状态想象
- 把最难返工的部分（Markdown 渲染、中文排版、代码高亮、TOC）前置 —— 这些改起来最贵
- 写入风险最高（动用户数据），放在最后，且闸门（`resolveArticleFile` / `writeFileAtomic`）已就位

**后果**
- 3a 完全不需要数据库（D1 的直接推论）
- 3a 结束时如果排版不满意，**不要进 3b** —— 否则写入做完还要回头改设计

**回头改的信号**：不存在（这是顺序，不是结构）。

## D3 · 文章 id = 由标题生成的 slug，创建时定下就不再改

**决定**：`id` 与文件名同一个东西（`transformer-basics.md`）。创建时由标题生成 slug，之后**标题怎么改都不重命名文件**；重名自动加 `-2`、`-3`。

**为什么**
- 人可读：在资源管理器里能认出是什么
- 稳定：id 不随标题变化 → 内部链接、收藏关联不会断
- 与 `lib/security/paths.ts` 的白名单 `[a-z0-9][a-z0-9-]{0,63}` 天然对齐

**后果**
- 需要处理重名
- ~~**未决问题（3b 前必须定）**：中文标题怎么生成 slug？~~ → **已由 D7 定案**（中文标题直接当文件名）
  - 拼音转写（要引入依赖，且多音字可能错）
  - 时间戳兜底（`note-20261029-ab12`，可读性差但零依赖）
  - 新建时让用户自己填（多一步操作，但最可控）

**回头改的信号**：如果开始频繁手动重命名文件来整理目录，说明"id 绑文件名"这个约束太紧。

## D4 · 写入入口：Server Action → service 层 → lib/content

**决定**
```
Server Action（app/(workspace)/**/actions.ts）
  └── features/<域>/service.ts      ← 业务规则，唯一决定"能不能写"的地方
        └── lib/content/*           ← 唯一碰文件系统的地方（走 resolveArticleFile + writeFileAtomic）
```
页面组件不得直接读写文件或数据库（需求书 §3 的要求，这里落成具体路径）。

**为什么**
- 少写一半代码：不用自己解析请求体、定错误格式
- Next 内建 Origin/Host 校验 → 阶段 7 的 CSRF 要求几乎白送
- 以后加 CLI 只是"另一个入口"，共用同一套校验和原子写入

**后果**
- 源码闸门已限制"只有 `lib/fs`、`lib/security/paths`、`lib/content` 能 import fs"；**3b 已落地第二条**：只有 `features/articles/service.ts` 能 import `lib/content/write` —— 页面想绕过 service 直接写文件，测试直接红
- 长任务（重建索引、备份）走 CLI 脚本，不走 HTTP

**回头改的信号**：需要外部脚本或手机快捷指令直接调 HTTP → 加一层 Route Handler 包同一个 service，不动下层。

## D5 · 笔记文件不进主仓库，放进独立的私有仓库

**决定**：`content/articles/` 被主仓库 gitignore；它本身是一个**独立私有 git 仓库**（和 `notes/`、`blog/` 同一模式：嵌套仓库 + 外层忽略）。

**为什么**
- 主仓库是**公开**的（GitHub `danri-web/ai-learning-lab`）：笔记一旦进主仓库就等于公开
- 独立私有仓库给到免费的版本历史 + 异地备份，同时不污染代码仓库

**后果**
- `clone` 主仓库后看不到任何笔记 —— 列表是空的（这是预期，不是 bug）
- 备份流程必须覆盖这个私有仓库（阶段 7）
- 想分享某篇笔记时，走"导出"，而不是"推仓库"

**回头改的信号**：如果开始想把笔记和代码一起版本化（比如想让别人看到示例笔记），
就加一个 `content/articles/_samples/`（单独例外放行），而不是把整个目录放回来。

## D6 · 中文搜索先用 LIKE，不急着上 FTS5

**决定**：阶段 5 先做 `LIKE` 全表过滤 + 前端排序；FTS5 作为"以后确实慢了再说"的备选。

**为什么**（都是实测，不是推测）
- FTS5 默认分词器 `unicode61` 对中文 **0 命中**（搜"注意力"找不到）
- 换 `trigram` 能用，但 **2 字词永远搜不到**（"模型""机制"全废），且中文 3-gram 索引体积膨胀明显
- 个人知识库规模（< 5000 篇）下，LIKE 的延迟完全可接受

**后果**
- 不需要维护索引一致性（正好符合 D1）
- 中文短词、子串匹配都天然支持

**回头改的信号**：搜一次超过 300ms，或用户开始要求"模糊/相关度排序"。
那时考虑 `Intl.Segmenter` 预分词（Node 内置，零依赖）+ unicode61，而不是直接上 trigram。

## D7 · 中文标题直接当文件名（取代 D3 的未决项）

**决定**：新建笔记时，`id` = 标题归一化后的结果：
1. NFKC 归一（全角 `ＡＩ` → `AI`）
2. 除了字母/数字/`-`/`_` 之外的一切连续字符折成一个 `-`（空格、冒号、括号、斜杠、emoji 都在内）
3. 去首尾 `-`、截到 64 位
4. 落在保留名上（`con`/`nul`/`com1`… 与路由保留字 `new`）就加 `note-` 前缀
5. 一个可用的字都没有 → 时间戳兜底 `note-20261030-ab12`

例：`Transformer 的注意力机制（上）` → `Transformer-的注意力机制-上.md`。
id 白名单从"纯 ASCII"放宽到 `[\p{L}\p{N}][\p{L}\p{N}\-_]{0,63}`。重名加 `-2`、`-3`。

**为什么**
- 可读性 > 自动化：这是用户每天在资源管理器里看的名字，`注意力机制.md` 比 `zhu-yi-li-ji-zhi.md` 和 `note-20261030-ab12.md` 有用得多
- 零依赖：拼音方案要引库，且多音字（银行/行走）会错，错在你天天看的文件名上
- 放宽的**只是字符集，不是结构**：点号、`/`、`\`、空格、控制字符、零宽字符仍然在白名单外 → `../` 这类路径穿越依旧进不来，`resolveArticleFile` 的物理校验也没动

**后果**
- 文件名、frontmatter 的 `id`、URL 里都会出现中文
- **实测坑（Next 16.4.3）**：动态段交给页面的 `params.id` 是**没解码的原始值**（`%E6%B3%A8...`），中文 id 会被路径闸门判成非法。所以页面入口统一走 `articleIdFromParam()`（含 `%` 才解码；id 字符集里没有 `%`，判据是安全的）。**升级 Next 必须重测这一条**
- 判重用"小写集合"：Windows 文件系统不分大小写，`Model.md` 与 `model.md` 是同一个文件，第二个自动变 `model-2`
- 标题里被折掉的字符不可逆（`注意力：机制` → `注意力-机制`），想保留原样只能改标题或手动改文件名
- 用户手写的额外 frontmatter 字段（比如 `reviewed: true`）在保存时**原样保留**，只覆盖 title/category/tags/updatedAt

**回头改的信号**：如果 URL 里的中文开始惹麻烦（分享链接被聊天软件截断、编码错乱），
就给"导出/分享"加一层 ASCII slug，而不是把文件名改回英文。

## D8 · 写入进程内串行 + 保存带版本校验（审计 v3 之后补的）

**决定**（两件，都是因为"写入会毁数据"）：
1. `lib/content/write.ts` 里所有会改磁盘的操作（新建/保存/删除）走**同一把进程内队列**（`serialize`）：
   分配 id 与落盘不能再被另一个请求插进来。
2. 编辑器打开时把**正文指纹**（sha256 前 32 位）放进隐藏字段 `base`；保存前比对磁盘上的当前指纹，
   不一致就拒绝（`reason: "stale"`），界面给出「仍然覆盖」按钮 —— 决定权在用户手里。
   不带指纹的调用（将来 CLI/脚本）不做检查，这是刻意的。

**为什么**
- 审计 v3 F1 实测：同一标题 8 路并发创建，**8 个请求都返回成功，磁盘上只剩 1 个 id**（7 份内容被静默覆盖）。
  原因不是原子写不够，而是"检查存在 → rename 顶替"是两步，中间能插进另一个请求。
- 审计 v3 F2 实测：两个编辑器先后保存，后保存的旧稿把新稿**静默**顶掉；外部编辑器改过、页面没刷新时同样如此。
  对"十年前写的笔记还要能打开"这个目标，静默丢失是最坏的一类。

**后果**
- 保存多读一次文件、算一次哈希（几十 KB，可以忽略）
- 外部程序的修改也会被算成"冲突"——这是对的：那确实是一次别人的写
- 没有版本历史可回退，所以「覆盖」必须由人显式点一次
- 跨**进程**的并发（两个 `next dev`、另跑 CLI）不共享这把队列，仍属残余 TOCTOU，已登记

**回头改的信号**：如果冲突提示频繁到让人烦（比如某个同步盘总在保存后重写文件），
再考虑"保存前自动重读+三方合并"——但那会引入真正的合并算法，代价远大于现在。

## D9 · 资源收藏：一个 `content/resources.json`，URL 只认 http/https

**决定**（阶段 4）：
1. 所有资源放**一个** `content/resources.json`（`{ version: 1, resources: [...] }`），和笔记一样
   **文件是真相**（D1）；这是个用户数据文件，主仓库 gitignore 掉，跟笔记一起备份。
2. URL **只接受 `http` / `https`**（`lib/security/resource-url.ts`）：`javascript:` / `data:` /
   `file:` / 相对路径 / 裸域名一律拒绝；**服务端永远不 fetch 用户给的地址**。
3. 写入复用笔记那套地基：进程内 `serialize`（D8）、`writeFileAtomic`、写前自检，
   外加单条资源的指纹（打开时记下，保存时比对，同 D8）。
4. 删除 = 从数组里移除 **+** 把这条记录追加到 `content/.trash/resources-deleted.jsonl`（带删除时间）。

**为什么**
- 几百条的规模下，一个 JSON 是**备份/回滚最便宜**的形态（拷一个文件就行），也能直接用任何编辑器修；
  没有"索引与文件不一致"的问题（D1 的红利），筛选/排序在内存里做，几百条是毫秒级
- 需求书 §8 要求避免 SSRF，而"只存链接、从不抓取"是最彻底的满足方式：没有请求，就没有 SSRF 面
- 拒绝 `file:` 是刻意的：浏览器对本地文件的策略各家不同，且以后加"打开链接"时要额外防

**后果**
- 改一条 = 重写整个文件（几百条约几十 KB；用原子写保证不会留半截）
- 文件坏了（非法 JSON / 结构不对）时应用**拒绝任何写入**，只在页面上报错 —— 不覆盖用户的坏文件
- 资源的 `id` 沿用笔记的规则（`lib/security/article-id.ts`），因为它是编辑页 URL 的一段
- 关联笔记是**逻辑关联**（存 `articleId`），不校验对方还在不在；断了就是列表上一条死链，不影响数据

**回头改的信号**：文件涨到 ~1MB、或保存一次超过 200ms、或开始需要"按标签统计/相关度"这类查询，
再按 D1 的原则加"可重建的索引缓存"（而不是换真相来源）；真到那一步再考虑 SQLite。

## 偏离需求书的记录（有意为之，不是遗漏）

| 需求书写的 | 实际用的 | 为什么 |
| --- | --- | --- |
| 代码高亮 **Shiki** | `rehype-highlight`（highlight.js） | Shiki 在 Turbopack 下被当成外部包，生成 `.next/<阶段>/node_modules/shiki-<hash>` 目录联接；Turbopack 下次启动会对它 `unlink`，而 Windows 对 junction 调 unlink 必然 EPERM —— **第二次 dev / 第二次 build 都起不来**（只能每次手动删 `.next`）。highlight.js 同步、无 wasm、无 junction；配色在 `app/globals.css` 里映射到设计令牌 |
| （未规定）Cache Components | `cacheComponents: false` | shadcn init 默认打开。开启后动态页必须写成 `<Suspense>` + `connection()`，与"整页 force-dynamic"互斥（构建直接报 `connection() accessed outside of <Suspense>`）。本地数据应用要的是"每次请求都读盘"，不是流式壳 |

**两处实现约束（不算偏离，但要知道）**：

- `lib/content/articles.ts` 里的 `articlesRoot()` 把 `content/articles` 写成**字面量**：Turbopack 静态分析不接受"用变量拼路径"，否则构建警告"会追踪整个项目"（实测会让 build 失败）。
- 读目录 / 读文件带 `/*turbopackIgnore*/`：正文是运行时读的用户数据，不该被打进产物。

## 残余风险登记（明知未解决，别再假装）

| 风险 | 现状 | 什么时候处理 |
| --- | --- | --- |
| TOCTOU：路径校验与真正读写之间有窗口 | 接受（本地单用户） | 如果将来多用户/多进程写同一目录 |
| **跨进程并发写**（两个 `next dev` / 另跑 CLI 写同一目录） | 进程内已串行（D8），跨进程仍是同一个窗口 | 真要支持时上文件锁（`proper-lockfile` 之类），而不是自己造 |
| 硬链接无法用 realpath 区分 | 不在防线内（它不能把写入搬出目录） | 不需要 |
| 目录没有 fsync | 未做（Windows 上收益接近零） | 如果将来要跑 Linux 服务器 |
| 无 CSP / 安全响应头 | 未做 | 阶段 7 |
| 无 ErrorBoundary | 未做 | 阶段 8 |
| 源码闸门是正则，不是沙箱 | 已知能绕过的形态已记录在测试里 | 阶段 8 用集成测试补 |
| **文件级符号链接的写入防护未经本机实测** | 本机建不出文件级 symlink（需管理员/开发者模式），对应断言显示 **skipped**（不是通过） | 任何能建的机器上会自动执行；在受限环境里必须看跳过的数量，不能只看绿色 |
| **未保存提醒只覆盖"关页面/刷新"** | `beforeunload` 已做；站内点击导航离开编辑页**不拦**（Next 目前没有官方的路由拦截钩子）。保存本身已有 D8 的版本校验兜底 | 如果真丢过一次内容，再上路由级拦截 |
| **删除的可恢复性只靠目录约定** | 文件进 `content/articles/.trash/`，界面没有"回收站"页，找回来要手动拖回 | 阶段 7（备份/恢复）时做成可视化的回收站 |
| **`.trash/` 会进那个私有 git 仓库** | 删除 = 多一个被跟踪文件，历史只增不减；"恢复"与 git 历史两套语义并存 | 阶段 7 备份设计时一起定（定期清理 or 降到 gitignore） |
| **资源删除的恢复只能手工** | 记录在 `content/.trash/resources-deleted.jsonl`，界面没有"回收站"，要自己把那行贴回 JSON | 阶段 7 做成可视化回收站 |
| **资源的关联笔记可能是死链** | `articleId` 只校验格式，不校验存在；笔记被删/改名后列表上会有一条点不开的链接 | 阶段 6 做任务关联时一起解决（或加"悬空引用"提示） |
| **Server Action 的 CSRF 依赖框架** | 依赖 Next 内建的 Origin/Host 校验；审计 v3 明确未验证该版本实现 | 阶段 7 做认证时用真实跨站请求验一遍 |
